# AIDE: AI 에이전트 아키텍처 — 에이전트 주도 개발을 위한 방법론

**AI 에이전트가 소프트웨어를 구축하는 방식은 바뀌고 있지만, 이를 이끄는 아키텍처 원칙은 여전히 인간 중심 시대에 머물러 있다.**

AIDE(Agent-Informed Development Engineering) 방법론은 실무자 경험, 학술 연구, 산업 프레임워크를 결합해 AI 에이전트 중심 소프트웨어 개발에 최적화된 일련의 원칙으로 정리한다.
핵심 통찰은 역설적이다. AI 에이전트 시대에는 오히려 훨씬 엄격한 엔지니어링 규율이 필요하다. 다만 기존 원칙을 그대로가 아니라 AI 문맥에 맞게 **중요하게 재해석**해야 한다는 점이다.

이 보고서는 AWS의 AI-DLC 프레임워크, Anthropic의 context engineering 연구, Thoughtworks의 Technology Radar, 학술 논문, 수많은 실무자 사례를 바탕으로, 비바이브 코딩 이후 시대의 포괄적 방법론을 제안한다.

---

## 1. 개발 방식은 바이브 코딩에서 에이전트 엔지니어링으로 이동했다

용어는 이미 흐름을 보여준다. Andrej Karpathy는 2025년 2월에 **"vibe coding"**이라는 용어를 만들었고, 이는 "완전한 직관 기반 코딩, 지수적 성장을 믿고 코드 자체를 잊는 방식"을 뜻했다.
정확히 1년 뒤 그는 이를 시대에 뒤떨어진 것으로 보며 **"agentic engineering"**을 제시했다. 여기서 그는 "기술과 과학, 전문성이 필요하다"고 강조했다.

Addy Osmani은 이를 스펙트럼으로 정리했다. vibe coding(YOLO) → AI-assisted engineering(중간) → agentic engineering(훈련·과학적 운영) 순서다.
모든 출처의 가장 중요한 발견은 하나다. **AI-assisted development는 전통 코딩보다 더 엄격한 엔지니어링 관행이 성과를 더 높인다**는 것이다.

이미 몇 가지 공식 방법론이 등장했다. AWS의 **AI-DLC**(AI-Driven Development Lifecycle)는 스프린트를 주 단위에서 **"bolts"**(시간/일 단위)로 전환하고 epic을 **"units of work"**로 대체한 매우 구조화된 방식이다.
학술계의 **V-Bounce Model**은 V-model을 AI 시대에 맞게 수정해 인간을 구현자에서 검증자로 전환한다.
OpenAI의 **AI-Native Engineering Team Guide**는 SDLC 각 단계에서 무엇을 위임하고 검토하며 소유할지 정의한다.
오픈소스의 **Agentic Coding Principles**는 6개 원칙과 28개 실천 항목을 정리한다.
이 모든 흐름의 공통된 주제는 단순하다. **인간은 코드를 쓰는 사람이 아니라 에이전트를 오케스트레이션하고 출력물을 검증하는 역할로 이동한다**.

Tweag의 통제 실험은 스펙 우선 방식과 강한 리뷰를 적용한 AI 보조 팀이 **45% 더 빠른 납기**와 높은 코드 품질을 동시에 달성했다고 보고했다.
반면 METR 연구는 엄격한 품질 기준을 유지하면 숙련된 개발자라도 작업 시간이 **19% 길어진다**고 보고했다.
즉, 속도만의 문제가 아니라 **속도와 품질의 균형**이 방법론의 핵심 난제다.

## 2. 원칙 1: 인간의 눈이 아니라 컨텍스트 윈도우를 기준으로 설계하라

AIDE에서 가장 구체적인 아키텍처 제약은 **context window**다. Context window가 백만 토큰이어도 `context rot`는 사라지지 않는다.
Chroma의 연구는 18개 LLM을 대상으로 입력 길이가 길어질수록 성능이 "점점 더 불안정"해짐을 보였다.
`lost in the middle` 효과 때문에 컨텍스트의 처음과 끝은 상대적으로 잘 잡히지만 중앙은 놓치기 쉽다.
Context size를 늘리는 것만으로 해결되지 않는다.

**파일 크기 규격**은 실무적으로 공통 합의점을 형성했다. 파일은 **200~300줄**, 최대 **500줄**이 실용적 기준이다.
Cursor 내부 연구 문헌은 Cursor IDE가 파일을 chunk 단위로 나누고 큰 파일에서 성능이 저하된다고 정리한다.
Ofer Shapira의 실무 규칙도 300줄을 권고한다.
AB Vijay Kumar 역시 vibe 코딩 맥락에서 동일 임계값에 도달한다.
수학적으로도 1줄당 약 **18 tokens**이면 300줄은 약 5,400 tokens로, 시스템 프롬프트·대화 이력·응답 여유를 합쳐도 상당히 안정적 범위다.

함수는 **작고 단일 목적이며 자기설명적**이어야 한다. 여러 AGENTS 규칙들과 cursor 규칙은 "멀티 모드 동작 없음", "플래그 파라미터로 분기 없음"을 반복한다.
핵심 원리는 **독립적 이해 가능성**이다. 각 파일이 충분한 네이밍, 타입, 구조로 많은 외부 파일을 열지 않아도 이해될 수 있어야 한다.
Thoughtworks의 Technology Radar는 context engineering을 중요하며, AI-Friendly code design을 Assess 기법으로 정식 소개한다.
이 프레임은 모델에 무엇을 노출하느냐를 설계하는 것이 핵심이며, 이는 순수 prompt engineering이 아니다.

## 3. 원칙 2: 무분별한 추상화보다 의식적 중복을 택하라

기존 개발의 DRY(Do not Repeat Yourself) 원칙은 가장 과감한 재해석이 필요하다.
공통된 결론은 Kirill Tolmachev가 정리했듯이, **"더 이상 절대 중복 금지로 보지 말고, 가시성을 가진 의식적 중복을 허용한다"**이다.
AI tooling은 지식 수준에서 DRY를 보장하면서 코드 수준에서 중복을 허용할 수 있게 도와주며, 이는 원래 DRY의 본래 의도와 맞닿아 있다.

경직된 DRY 반대의 근본 논거는 구조적이다.
Factory.ai 연구는 AI 에이전트의 multi-hop reasoning 취약성을 보였다. 즉 다단계 추상화 체인을 추적해 동작을 이해해야 하는 코드가 AI에 취약하다.
관련 코드를 한 곳에 모아둔 self-contained 모듈은, 다섯 개 파일을 넘나들어야 이해되는 DRY 코드보다 훨씬 쉬워진다.
**지역성(Locality)**, 즉 관련 코드를 묶어두는 장점은 AI 이해도를 대폭 향상시킨다.

그러나 Tolmachev는 반대 논리도 지적한다. AI가 중복을 추적하기 어렵다고 해서 중복을 허용하면 코드가 과하게 늘어나 context window를 초과해 오히려 DRY가 필요해진다는 것이다.
해결은 **AHA (Avoid Hasty Abstractions)**다.
Kent C. Dodds의 "두 번 이상 패턴을 본 뒤 추상화"와 Sandi Metz의 "잘못된 추상화보다 중복을 선호"가 다시 중요해진다.

AIDE의 입장:

- **비즈니스 지식 수준에서는 DRY를 강제**한다. 하나의 비즈니스 규칙은 단일 출처여야 한다.
- **코드 유틸리티 수준에서는 중복 허용**한다. 소규모 헬퍼가 반복되어도 좋다.
- **중복 코드 drift는 AI 에이전트를 검토 단계에 투입해 감지**한다.

Faros AI는 "에이전트는 함수 존재 여부를 먼저 묻지 않고 그대로 출력한다"고 경고한다. 즉 DRY 위반에 취약하다.
명시적 지시 파일과 리뷰 프로세스로 이를 상쇄해야 한다.

## 4. 원칙 3: 함수형 코어 + 아키텍처 셸

OOP냐 함수형이냐의 문제는 혼합형으로 정리된다.
**함수형은 AI 코드 생성에 구조적 장점이 있다**. LLM은 본질적으로 stateless 상태에서 입력별로 처리되며, 순수 함수는 이 특성과 잘 맞는다.
Context window가 한정된 환경에서는 side-effect 없는 작은 self-contained 함수가 생성과 검증이 쉽고, 불변성은 상황 인식이 제한된 AI 코드에서 예기치 않은 버그를 줄인다.

OOP는 구조 조직 측면에서 여전히 가치가 있다. Clean Architecture 실무자들은 명확한 경계(클래스/인터페이스/모듈)가 AI 에이전트의 네비게이션을 돕는다고 본다.
권장 패턴은 **"functional core, imperative shell"**이다.
비즈니스 로직은 순수 함수(FP)로, 구조 조직은 클래스 기반과 아키텍처 패턴으로 분리한다.
직접적으로 FP vs OOP를 AI 코드 생성으로 비교한 벤치마크는 아직 제한적이며, 현재 HumanEval/SWE-bench은 함수 단위 Python에 치우쳐 상대적으로 FP 스타일에 유리할 수 있다.

기존 설계 원칙의 우선순위는 다음처럼 재정렬된다.

- **DDD(Domain-Driven Design)**는 더 중요해진다. 유비쿼터스 언어를 에이전트 경계별로 문서화해야 AI 협업이 안정적이다. Rod Johnson의 DICE(Domain-Integrated Context Engineering)가 DDD와 LLM context를 연결한다.
DDD가 없으면 대규모 에이전트 생태계는 "Big Ball of Mud"가 되기 쉽다.
- **Clean Architecture**는 매우 적합하다. 의존성 규칙(내부 레이어는 외부 레이어에 의존하지 않음)은 예측 가능한 구조를 준다. 2025~2026년 실무자들 다수는 AI 코딩 에이전트에서 실제로 "매우 잘 동작"한다고 보고한다.
  프레임워크 독립성은 LLM/도구 교체에 결정적이다.
- **Hexagonal Architecture**를 강하게 권고한다. 포트/어댑터는 비즈니스 로직을 인프라와 분리해 급변하는 AI 생태계에서 LLM 교체를 쉽게 만든다.
  도메인 로직은 코드에 있고, AI 에이전트는 앱 레이어에 위치하고, 어댑터는 LLM API/DB/벡터 저장소를 처리한다.
- **SOLID 원칙**도 AI 기준으로 우선순위를 바꿔야 한다: **DIP > SRP > ISP > LSP > OCP**.
  DIP가 핵심이다(추상화 의존이 필요). SRP는 변경 범위를 제한한다.
  ISP는 좁고 최소 인터페이스로의 경계가 AI에 유리하다. OCP는 AI가 코드를 수정할 수 있다는 점 때문에 재해석이 필요하지만, 플러그인 아키텍처에서는 여전히 유효하다.
- **GoF 패턴**은 AI 친화형/비친화형이 존재한다.
  Strategy, Observer, Factory, Adapter, Command는 양호하고, Visitor(복합 더블 디스패치), 깊은 Abstract Factory 체인, 긴 Decorator 체인은 문제를 유발한다.

## 5. 원칙 4: 테스트는 AI의 사양 언어다

TDD는 AI 에이전트와 더 중요해졌다.
이는 David Luhr가 말한 "prompt engineering"의 한 형태다.
David Luhr는 "테스트 없이 생성 코드가 무엇을 해야 하는지의 사고가 빠진다"고 본다.
Matthews & Nagappan의 학술 검증도 GPT-4/Llama 3에서 문제 진술과 함께 테스트를 제공할 때 결과가 개선됨을 보인다.

권장 워크플로우는 **Test-Driven Generation(TDG)**다.

1. 인간이 사양을 작성하거나 승인
2. AI가 테스트 케이스를 생성(Red)
3. AI가 테스트를 통과하는 구현 생성(Green)
4. AI가 보호된 경계 안에서 리팩터링
5. 인간이 테스트와 구현 모두 검토

핵심 경고: AI가 테스트와 코드를 모두 쓰면 confirmation bias가 생긴다. 즉 코드 버그를 통과하는 테스트를 만들 수 있다.
해결은 테스트 작성 주체를 분리하거나, 다른 AI 모델을 쓰거나, 사람이 사양을 직접 쓰는 것이다.

**Property-Based Testing(PBT)**는 가장 중요한 새로운 패턴이다.
Property-Generated Solver 연구는 TDD 대비 **23.1~37.3% 상대적 개선**을 보여준다.
핵심 통찰은 LLM이 완전한 코드 자체보다 정합성 **속성(property)**을 생성할 때 훨씬 잘한다는 점이다.

"Hard" 작업에서 직접 코드는 정확도 1.1%인 반면, 검증 생성은 **48.9%**까지 올라간다.
PBT는 self-deception 순환을 깨는 접근이다. 속성은 정확한 입출력 맵 없이 본질적 정합성을 포착하기 때문이다.
AWS의 Kiro IDE는 워크플로 전체에서 PBT를 통합했다.

보안 테스트는 필수다.
2025년 Veracode 보고서에 따르면 AI 생성 코드의 약 **45%**에 보안 결함이 있으며 Java는 72%로 가장 높다.
논리 오류는 human-written 대비 **1.75배**.
XSS는 **2.74배**.
모델 크기를 키워도 보안 성능은 개선되지 않는 경향이 있다.
즉 더 큰 모델이 더 안전하다는 보장은 없다.

## 6. 원칙 5: 계층적 context engineering을 통한 지시 파일 구조

AI 에이전트 지시 인프라는 급속히 성숙했다.
AGENTS.md는 사실상 표준으로 자리잡았고, 현재 60,000개 이상 오픈소스 프로젝트에서 사용되며 OpenAI Codex, Google Jules, Cursor, GitHub Copilot 등과 여러 도구가 지원한다.
Linux Foundation 산하 Agentic AI Foundation이 이를 관리한다.
CLAUDE.md는 Claude Code 전용 구현체로, 계층 로딩과 lazy evaluation 같은 추가 기능을 포함한다.

권장 구조는 **점진적 노출**이다.

- **1단계: 항상 로딩** (루트 CLAUDE.md/AGENTS.md): 규약, 기술 스택, 핵심 명령, 아키텍처 개요. **300줄 이하**로 유지. 연구상 규칙 수 증가가 명령 이행률을 선형 하락시킨다
- **2단계: 지연 로딩** (하위 디렉토리 파일): 해당 디렉토리에 작업할 때만 로드
- **3단계: 필요 시 로딩** (agent_docs/, references/): 깊은 문서는 필요시에만 읽음. SKILL.md는 YAML frontmatter로 선택적 활성화되는 역량 패키지를 제공

내용은 **What/Why/How** 프레임을 따라야 한다.
- What: 기술 스택, 구조는 무엇인가
- Why: 컴포넌트 존재 이유는 왜인지
- How: 에이전트 작업 방식(명령, 패턴, 제약)

중요 지침: LLM에게 linter 역할을 맡기지 말라. 스타일 강제는 결정론적 도구를 사용하고, 지시 파일은 아키텍처와 비즈니스 맥락에 집중시켜야 한다.
추상적 규칙보다 실제 예시가 더 중요하다. 좋은 코드 예시와 피해야 할 레거시 예시를 함께 보여야 한다.

크로스 도구 일관성을 위해 rulebook-ai 같은 도구가 단일 정의에서 여러 도구 형식으로 변환한다.
Cursor의 `.mdc`, Windsurf의 `.windsurfrules`, Cline의 `.clinerules/`, GitHub Copilot의 `.github/copilot-instructions.md`처럼 분산되었던 형식은 현재 MCP/AGENTS 조합으로 관리 가능하다.

**MCP(Model Context Protocol)**는 지시 파일을 보완한다.
MCP는 에이전트가 외부 도구와 데이터 소스에 연결하는 표준이고, Skills는 수행 방법(know-how), MCP는 실행 능력(capability)을 제공한다.
두 체계 모두 컨텍스트를 한 번에 다 올리지 않도록 점진적으로 로딩한다.

---

## 7. 원칙 6: 병렬 에이전트를 위한 저장소·팀 아키텍처

AI 에이전트에게 monorepo는 큰 장점이 있다.
AI는 frontend와 backend API의 연결을 한 번에 이해하고, 싱글 PR에서 여러 프로젝트 변경을 원자적으로 처리할 수 있다.
동일한 규칙을 더 일관되게 적용하기 쉬워진다.
또한 AI는 monorepo의 전통적 복잡성 비용을 완충한다. 과거 수 주 걸리던 대규모 마이그레이션이 시간 단위로 줄어들 수 있다.

반면 장점도 있지만, 규제 환경에서는 멀티 레포가 보안 경계에서 더 명확할 수 있다는 단점/트레이드오프가 있다.

AI 내비게이션에 맞춘 저장소 구조는 AGENTS.md에 코드베이스 맵을 명시하고, 핵심 디렉토리를 명확한 이름으로 구성하는 것이다.
모든 AGENTS.md는 설명자적 가이드가 아닌 실제 지점을 가리키는 지도 역할을 해야 한다.
기능 단위 디렉토리를 default로 작고 집중적으로 나눈다.
monorepo에서는 하위 CLAUDE.md를 통해 component 단위 context를 지연 로딩한다.

팀 워크플로우는 **멀티 에이전트 병렬성**으로 이동한다.
실무자들은 같은 브랜치에서 3~5개의 Claude Code 인스턴스를 tmux로 분리해 각기 범위가 명확한 작업을 수행한다.
git-town, Graphite 같은 도구가 병렬 변경사항을 관리한다.
80/20의 의미도 바뀐다. **코드는 AI가 80% 작성하고, 검토와 수정은 20%의 시간**이 든다.

코드 리뷰도 근본적으로 변한다. AI 도입 후 PR은 크기가 약 **18% 증가**했지만, PR당 사고는 **24% 증가**, 변경 실패율은 **30% 증가**한다.
그래서 최근의 PR Contract는 다음을 요구한다:
- 의도 진술
- 동작 증명(테스트/데모)
- 위험 등급과 AI 기여 공개
- 사람이 집중 검토해야 할 부분

AI가 생성한 코드는 "도움이 되는 초안"으로 다루고, 설명 불가한 코드는 커밋하지 않는다.
또한 생성 모델과 리뷰 모델을 분리해 에코 챔버를 방지한다.

**타입 주석/타입 애너테이션**은 결정적으로 중요하다.
구조화된 타입은 AI의 생성/네비게이션 품질을 크게 높인다.
TypeScript strict mode는 plain JavaScript보다 큰 이점을 준다.
Python type hint + Pydantic 자동 스키마는 AI가 효과적으로 소비한다.
모든 지시 파일에서 타입 주석을 강제해야 한다.

## 8. 원칙 7: 인간의 역할은 구현자에서 아키텍트-리뷰어로 이동

AIDE는 SDLC 전반에서 인간 역할을 재정의한다.

- **요구사항 & 아키텍처**: 인간이 전적으로 소유한다. 핵심 아키텍처 결정, 도메인 모델링, bounded context 정의, 보안 설계는 인간 주도다.
- **사양**: 인간이 작성/승인한다. 사양 우선 접근이 AI 코드 품질의 가장 큰 예측 지표다.
AWS AI-DLC의 **Mob Elaboration**는 PM·개발자·QA가 초기부터 AI와 협업한다.
- **구현**: 인간은 경계가 분명한 작업을 에이전트에 위임한다. 빠른 주니어 팀을 운영하듯 "작성 후 리뷰"가 기본이다.
- **테스트**: 인간은 테스트 의도와 사양을 소유한다. AI는 테스트 코드와 구현을 생성한다. PBT 속성은 인간이 리뷰해야 한다.
- **리뷰**: AI가 놓치는 지점을 사람이 처리한다(보안 취약점, 아키텍처 드리프트, 도메인 문맥, 조직 지식).
AI는 1차 리뷰(스타일/명백한 버그)로 보조할 수 있다.
- **운영**: AI는 사고 대응, 모니터링, 자동 복구를 지원하되 인간이 정의한 guardrail 안에서 작동한다.

중요한 형평성 이슈로, agentic engineering은 도메인 이해도가 높은 시니어에게 더 큰 이익을 준다.
반면, 단순히 수동 수용만 하는 초보자는 기본기 저하 위험이 생긴다.
방법론은 주니어가 지침을 보면서 학습하고 성장할 수 있는 길을 별도로 제공해야 한다.

## 9. 결론: 일곱 가지 원칙으로 본 AIDE 방법론

AIDE 방법론은 기존 상식의 뒤집힘에 기초한다.
코드 생성이 저렴해질수록 아키텍처 규율은 더 가치가 높아진다는 점이다.
일곱 가지 원칙 — **Context-window-aware sizing, 의식적 중복, 기능 핵심/구조 셸, 테스트 기반 생성, 계층 지시 파일, 병렬 에이전트 저장소 설계, 인간 아키텍트-리뷰어 역할** —은 서로 보완적 통합 프레임을 이룬다.

핵심으로 세 가지 통찰이 나온다.
첫째, **context window가 새로운 CPU다**. 과거의 메모리와 처리 성능이 하드웨어 제약이었다면, 지금은 context가 제약이자 설계 중심이다.
둘째, **DRY는 폐기되지 않고 변형**된다. "코드 중복을 금지"에서 "지식 중복을 금지"로 이동한다. 즉 코드 단위 반복은 locality와 에이전트 이해를 높이면 허용 가능하다.
셋째, **테스트가 사양 언어화된다**. 구현 이후 검증이 아니라, 인간이 AI 에이전트에게 의도를 전달하는 주 메커니즘이 된다.

현장은 빠르게 변한다.
AWS AI-DLC는 이미 기업에 배치되었고, AGENTS.md는 1년 내 60,000개 이상의 저장소를 넘었다.
Karpathy가 vibe coding을 12개월 뒤 obsolete로 선언한 것도 같은 흐름이다.
AIDE는 정적 문서가 아니라 진화형 프레임워크다. 버전관리되고 반복되며 AI 에이전트 성능 향상과 커뮤니티 학습 심화에 맞춰 계속 업데이트되어야 한다.
